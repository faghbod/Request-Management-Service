# سرویس مدیریت درخواست سازمانی

این سولوشن درخواست‌های Financial، Legal و Technical را ثبت می‌کند و آن‌ها را به کارشناسان واجد شرایط تخصیص می‌دهد. ساختار پروژه Clean و ساده است و از Repository و Unit of Work استفاده می‌کند؛ در این پروژه DDD یا CQRS پیاده‌سازی نشده است.

## معماری و لایه‌ها

- `OrganizationRequests.Domain` شامل موجودیت‌ها، enumها و قراردادهای Repository و Unit of Work است.
- `OrganizationRequests.Application` منطق ثبت، صف، انتخاب کارشناس، تخصیص و بستن درخواست را در سرویس‌ها نگه می‌دارد. DTOها و کلاس‌های Mapping نیز در همین لایه هستند.
- `OrganizationRequests.Infrastructure` قراردادهای ذخیره‌سازی را با EF Core و SQL Server پیاده‌سازی می‌کند. پیکربندی Fluent API، `DbContext` و migrationها نیز اینجاست.
- `OrganizationRequests.Api` ورودی HTTP، احراز هویت و ثبت وابستگی‌های API را فراهم می‌کند.
- `OrganizationRequests.Worker` یک فرایند میزبانی‌شده‌ی جدا برای پردازش صف است.
- `OrganizationRequests.Tests` آزمون‌های منطق برنامه و یکپارچگی را نگه می‌دارد.

وابستگی‌ها به سمت منطق برنامه می‌روند: Application به قراردادها و Domain وابسته است و Infrastructure پیاده‌سازی آن قراردادها را فراهم می‌کند. API و Worker ترکیب وابستگی‌ها را انجام می‌دهند.

## چرا عملیات‌ها async هستند؟

بخش زیادی از زمان سرویس صرف انتظار برای پاسخ SQL Server می‌شود. `async` و `await` در عملیات ورودی/خروجی مثل query، ذخیره‌سازی و انتظارهای Worker، هنگام انتظار thread را اشغال نگه نمی‌دارند. این کار ظرفیت سرویس برای رسیدگی به کارهای هم‌زمان را بهتر می‌کند؛ لزوماً زمان اجرای یک query منفرد را کمتر نمی‌کند. `CancellationToken` هم برای توقف کنترل‌شده به عملیات پایگاه داده و delayها منتقل می‌شود.

## Worker و عمر سرویس‌ها

`AssignmentWorker` از `BackgroundService` مشتق شده و با `AddHostedService` به‌عنوان سرویس singleton ثبت می‌شود. در مقابل، سرویس‌های Application و `DbContext` از نوع scoped هستند و نباید مستقیماً در سازنده‌ی یک singleton تزریق شوند؛ در غیر این صورت وابستگی scoped ممکن است بیش از عمر مجازش نگه داشته شود.

برای حل این تفاوت عمر، Worker از `IServiceScopeFactory` استفاده می‌کند و هنگام خواندن صفحه‌ی صف یک scope کوتاه‌عمر می‌سازد. برای هر تلاش تخصیص، از جمله retry، scope تازه‌ای می‌سازد و سرویس scoped را از همان scope می‌گیرد. با پایان عملیات scope و `DbContext` آن dispose می‌شوند و state ردیابی‌شده‌ی تلاش قبل وارد تلاش بعدی نمی‌شود.

Worker به‌صورت دوره‌ای ردیف‌های `PendingAssignment` را از جدول `ServiceRequests` می‌خواند. درخواست‌ها صفحه‌بندی می‌شوند تا کل صف یک‌جا در حافظه بارگذاری نشود؛ cursor کلیدمحور صفحه‌ی بعد را مشخص می‌کند و اولویت مؤثر، زمان ثبت و شناسه ترتیب را تعیین می‌کنند. در هر چرخه درخواست‌ها یکی‌یکی پردازش می‌شوند تا نتیجه‌ی تخصیص قبلی و شمارنده‌ی به‌روزشده‌ی ظرفیت در انتخاب درخواست بعدی اثر بگذارد. تعارض‌های قابل‌تکرار با تعداد محدود و فاصله‌ی افزایشی دوباره امتحان می‌شوند.

## Idempotency ثبت درخواست

کلاینت برای هر عملیات ثبت، `RequestKey` می‌فرستد. اگر همان کاربر همان کلید و همان موضوع و اولویت را دوباره بفرستد، سرویس همان درخواست قبلی را برمی‌گرداند. استفاده از کلید برای کاربر دیگر یا با محتوای متفاوت، تعارض ایجاد می‌کند.

سرویس ابتدا کلید را جست‌وجو می‌کند؛ علاوه بر آن، روی `RequestKey` ایندکس یکتا در دیتابیس وجود دارد. بنابراین اگر دو ثبت هم‌زمان از بررسی اولیه عبور کنند، فقط یکی درج می‌شود. سرویس خطای نقض یکتایی را تشخیص می‌دهد، رکورد موجود را دوباره می‌خواند و همان قاعده‌ی کاربر و محتوا را اعمال می‌کند. این سازوکار تکرار درخواست HTTP را کنترل می‌کند؛ به‌تنهایی Inbox Pattern نیست.

## هماهنگی ظرفیت کارشناس و RowVersion

`Expert.ActiveRequestCount` تعداد درخواست‌های فعال کارشناس را نگه می‌دارد و دیتابیس محدودیت می‌گذارد که این مقدار بین صفر و `Capacity` باشد. هنگام تخصیص، افزایش شمارنده، تغییر وضعیت درخواست و ثبت تاریخچه در یک تراکنش انجام می‌شوند. اگر بخشی از عملیات شکست بخورد، تراکنش rollback می‌شود و تغییرات با هم ثبت نمی‌مانند.

روی رکورد `Expert`، فیلد `RowVersion` با Fluent API به‌عنوان SQL Server `rowversion` تنظیم شده است. EF Core مقدار نسخه‌ای را که هنگام خواندن دیده، هنگام update بررسی می‌کند. اگر عملیات هم‌زمانی همان رکورد را زودتر تغییر داده باشد، نسخه عوض شده و ذخیره‌ی عملیات بعدی با تعارض هم‌زمانی روبه‌رو می‌شود؛ تراکنش rollback و تعارض قابل‌تکرار دوباره امتحان می‌شود.

`RowVersion` قفل یا lock روی کل جدول نیست؛ یک سازوکار **optimistic concurrency** برای تشخیص تغییر رکورد بین خواندن و نوشتن است. همچنین تخصیص درخواست با `UPDATE` شرطی انجام می‌شود که فقط وقتی ردیف هنوز `PendingAssignment` و تخصیص‌نیافته باشد، آن را تغییر می‌دهد. این شرط از تخصیص دوباره‌ی یک درخواست در رقابت هم‌زمان جلوگیری می‌کند.

## ارتباط موضوع درخواست و تخصص کارشناس

نوع درخواست و تخصص کارشناس هر دو از enum مشترک `RequestSubject` استفاده می‌کنند. درخواست یک `Subject` دارد؛ کارشناس می‌تواند چند `ExpertSpecialty` داشته باشد. تنها کارشناسی که تخصص متناظر با درخواست را دارد، کاندید تخصیص است. شمارنده و ظرفیت کارشناس بین همه‌ی تخصص‌های او مشترک است، نه جداگانه برای هر تخصص.

## الگوریتم انتخاب کارشناس

از بین کارشناسان فعال و حذف‌نشده‌ای که تخصص مناسب و ظرفیت خالی دارند، این ترتیب اعمال می‌شود:

1. کمترین نسبت درخواست فعال به ظرفیت انتخاب می‌شود. نسبت‌ها با ضرب متقاطع مقایسه می‌شوند تا تقسیم اعشاری لازم نباشد.
2. اگر نسبت برابر باشد، کارشناس با ظرفیت باقی‌مانده‌ی بیشتر اولویت دارد.
3. اگر ظرفیت باقی‌مانده هم برابر باشد، زمان جدیدترین تخصیص باز هر کارشناس مقایسه می‌شود؛ کارشناسی که از آخرین تخصیص بازش زمان بیشتری گذشته، اولویت می‌گیرد. تخصیص‌های بسته یا حذف‌شده محاسبه نمی‌شوند و موضوع درخواست باز هم محدود به تخصص فعلی نیست.
4. اگر هنوز برابر باشند، شناسه‌ی کوچک‌تر برای نتیجه‌ی پایدار انتخاب می‌شود. کارشناسی که هیچ تخصیص بازی ندارد، از کارشناسی دارای زمان تخصیص جلوتر است.

## چرا Inbox Pattern نداریم؟

در این جریان پیام مستقلی از message broker یا سامانه‌ی بیرونی دریافت نمی‌کنیم که شناسه‌ی تحویل آن را در جدول Inbox ثبت کنیم. خود ردیف `ServiceRequests` با وضعیت `PendingAssignment` کارِ باقی‌مانده را به‌شکل پایدار در دیتابیس نگه می‌دارد و Worker آن را با polling پیدا می‌کند.

پردازش تخصیص در یک تراکنش، شمارنده‌ی کارشناس، وضعیت درخواست و تاریخچه را با هم ثبت می‌کند. اگر عملیات شکست بخورد، rollback می‌شود و درخواست در وضعیت انتظار باقی می‌ماند تا چرخه‌ی بعدی Worker دوباره آن را بررسی کند. چون منبع کار همان ردیف درخواست است و پیام خارجی برای ثبت/مصرف نداریم، جدول Inbox جداگانه در این معماری داده‌ی تکراری و سازوکار اضافی ایجاد می‌کرد.

## اجرای محلی

پروژه برای .NET 8 و SQL Server تنظیم شده است. پس از تنظیم connection string و مقادیر لازم JWT در محیط توسعه:

```powershell
dotnet restore OrganizationRequests.sln
dotnet run --project src/OrganizationRequests.Api
dotnet run --project src/OrganizationRequests.Worker
```

API و Worker دو فرایند جدا هستند و هر دو به همان پایگاه داده نیاز دارند. Migrationها باید جداگانه و با مقصد بررسی‌شده اعمال شوند؛ Worker هنگام اجرا دیتابیس را خودکار تغییر نمی‌دهد.
